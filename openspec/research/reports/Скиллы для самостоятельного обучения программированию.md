# Создаём учебные скиллы под свои границы

**Создавать свои четыре скилла имеет смысл.** Близкие готовые решения существуют, поэтому придумывать методику с нуля не нужно. Однако среди проверенных вариантов не найдено точного сочетания твоих требований: пользователь сам выбирает режим, в строгом режиме самостоятельно пишет код, в совместном получает реализацию только отдельных частей, а ускорение не снимает эти ограничения. Основное отличие твоей идеи — устойчивые границы авторства, а не особый способ задавать вопросы. Разумный путь — написать короткие собственные инструкции, используя удачные механики найденных наставников. Это вывод по прочитанным первоисточникам, а не доказательство отсутствия подходящего скилла во всём интернете.

## Готовые наставники близки по методике, но отличаются границами

Сравнение ниже опирается на реальные `SKILL.md` и связанные инструкции. Названия «учебный» и «сократический» сами по себе не означают запрета готового решения: у нескольких кандидатов предусмотрен переход к нему по прямой просьбе.

| Кандидат и первоисточник | Что полезно для твоих скиллов | Что придётся изменить |
|---|---|---|
| [TuTor](https://raw.githubusercontent.com/kevinnio/tutor/master/SKILL.md) | Ученик пишет код; агент ведёт по одному действию и проверяет результат. Запрет исправлять за ученика сохраняется при просьбе об исключении. | Самостоятельные проверки ограничены: тесты повторяются после ученика, запуск приложения запрещён. Тебе нужна более активная проверка проекта агентом. ([Tool gate](https://raw.githubusercontent.com/kevinnio/tutor/master/references/tool-gate.md)) |
| [Think Before Code: dsa-tutor](https://raw.githubusercontent.com/Far-200/think-before-code/main/skills/dsa-tutor/SKILL.md) | Рассуждение через примеры, инварианты, крайние случаи и сложность; подсказки доходят до неполного псевдокода. | После рассуждения и прямой просьбы допускает полную реализацию. Ориентирован преимущественно на алгоритмические задачи. |
| [socratic-code-mentor](https://gist.github.com/ogzhanolguncu/274e9974dc02942109ad70200f6d7b25) | Уровни с проверяемым результатом, перечитывание изменений и запуск тестов перед продолжением. | Агент пишет вспомогательную часть самостоятельно и может закончить за пользователя по просьбе. |
| [algo-sensei](https://raw.githubusercontent.com/karanb192/algo-sensei/main/SKILL.md) | Распознавание алгоритмических паттернов, объяснение выбора и постепенные подсказки. | [Tutor mode](https://raw.githubusercontent.com/karanb192/algo-sensei/main/modes/tutor-mode.md) включает готовую реализацию; нет границы одной совместно выполняемой части. |
| [engineering-growth-mentor](https://raw.githubusercontent.com/EDM115/skills/master/skills/engineering-growth-mentor/SKILL.md) | Поиск существующих решений в проекте, обучение на реальных изменениях, проверка понимания. | Не запрещает выполнять задание целиком; некоторые команды и проверки привязаны к предварительному одобрению плана. |
| [Flagrare tutor](https://raw.githubusercontent.com/Flagrare/agent-skills/main/plugins/flagrare/skills/tutor/SKILL.md) | Один вопрос за ход, ступени помощи, работа с текущим кодом. | В ряде веток допускает полное раскрытие ответа по просьбе; дополнительные интеграции не нужны для твоей задачи. |

**Ближайшая основа строгого режима — TuTor**, совместного — механика этапов `socratic-code-mentor`. Для переносимых методов особенно интересен отдельный [pattern-transfer-coach](https://raw.githubusercontent.com/Far-200/think-before-code/main/skills/pattern-transfer-coach/SKILL.md): после решения он предлагает выделить структуру метода, признаки его применимости и перенести идею на другую задачу. Такой небольшой разбор после завершения даст больше пользы твоей цели, чем постоянный поиск необычного алгоритма ради необычности.

## Официальный Learning оставляет человеку только выбранные участки

Anthropic Learning предлагает другой договор: агент выполняет рутинную реализацию, оставляет человеку содержательные участки с `TODO(human)`, ждёт их выполнения и продолжает. Это полезно для участия в разработке, но **не соответствует правилу «весь код пишу я»**. Оно также не задаёт твоего ограничения совместного режима — реализовывать лишь запрошенные части задания. ([Официальная документация](https://code.claude.com/docs/en/output-styles))

Официальный плагин внедряет инструкции при старте сессии, а его README описывает человеческие вклады примерно по 5–10 строк. Поэтому установка плагина не заменяет четыре режима, которые ты хочешь явно выбирать через `$`. Из него полезно взять принцип содержательного участия ученика, без автоматического написания агентом всей обвязки. ([Плагин Learning](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/learning-output-style))

## Четыре коротких режима сохранят нужные различия

Предлагаемые, пока не окончательно согласованные имена отражают две независимые оси:

| Вызов | Начало работы и граница помощи |
|---|---|
| `$study-hint-normal` | Сначала выяснить твою идею; давать подсказки постепенно. Реализацию пишешь ты, псевдокод разрешён. |
| `$study-hint-fast` | Минимум вопросов, более явные и короткие подсказки. Право писать код остаётся только у тебя. |
| `$study-guide-normal` | Сразу предложить понятный подход. Писать по просьбе отдельную часть, сохраняя совместную работу. |
| `$study-guide-fast` | Короткий план и предметная помощь с текущей частью. Всё задание целиком агент не выполняет. |

Общее ядро — изучить условие и существующий проект, выбрать понятный переносимый метод, объяснить его применимость, читать твои изменения и запускать подходящие проверки. Поиск в интернете разрешён и нужен по содержательной необходимости. Различие темпов касается подробности и прямоты помощи, а не права выдавать готовую работу.

Осталось согласовать два практических края. Первый — насколько подробным может быть псевдокод: полное описание всего алгоритма способно оставить только перевод в синтаксис. Второй — когда совместный режим останавливается между частями. **Рекомендую ожидать твоего вклада или обсуждения результата перед продолжением**: иначе агент сможет формально разделить работу на функции и написать их все подряд. Это рекомендация для согласования, а не уже установленное правило.

## Заимствуем механики и проверяем поведение

Для этой задачи не нужны персонажи, очки опыта, журналы прогресса или дополнительные плагины. Четыре небольших самостоятельных скилла проще прочитать и переносить. При буквальном копировании чужих инструкций необходимо учитывать их лицензию: MIT подтверждена для [TuTor](https://raw.githubusercontent.com/kevinnio/tutor/master/LICENSE) и [Think Before Code](https://raw.githubusercontent.com/Far-200/think-before-code/main/LICENSE); наличие лицензии у одного проекта не распространяется автоматически на другие.

После согласования границ полезнее проверить несколько реальных диалогов, чем расширять инструкции заранее: просьбу сделать всё задание, просьбу написать одну функцию, затруднение без попытки и найденную тестами ошибку. Проверять следует и обычный, и быстрый темп. Скилл задаёт поведение, но не является техническим барьером, гарантирующим соблюдение правил; аналогичное различие инструкций и гарантий отмечает [документация Anthropic](https://code.claude.com/docs/en/output-styles).

Установка найденных решений и испытания на моделях не проводились; исследование завершено на уровне документации и исходных инструкций. Следующий полезный результат — собственные короткие скиллы с проверенным сохранением самостоятельности ученика, а не ещё один большой учебный фреймворк.
