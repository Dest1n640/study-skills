## Context

Мотивация описана в [proposal.md](proposal.md). В проекте четыре самостоятельных SKILL.md, два README и два файла evaluation; исполняемого набора фикстур и сохранённых ответов нет. Git-репозиторий пока не инициализирован, поэтому идентификацию проверенной версии нельзя основывать только на commit SHA.

Рядом с продуктом находятся шесть OpenSpec-скиллов. Текущая реализация [Skills CLI discovery](https://github.com/vercel-labs/skills/blob/main/src/skills.ts) просматривает каталоги агента наряду с skills/. Это основание проверить состав установки, а не утверждение об уже воспроизведённой ошибке установки.

Design нужен из-за связи упаковки, спецификаций и оценки поведения. Сами учебные инструкции в основном уже соответствуют замыслу.

## Goals / Non-Goals

**Goals:** повторяемая процедура проверки на небольших синтетических задачах, явный состав установки, сценарии существующих правил, проверяемые ссылки на доказательства.

**Non-Goals:** разработка eval-платформы, измерение эффективности обучения, удаление служебных скиллов, публикация, выбор лицензии, универсальный сертификат совместимости. Прямую загрузку SKILL.md не выдаём за проверку нативного вызова.

## Decisions

### 1. Дополнить существующие capability, сохранив продукт

Дельты относятся к study-modes и distribution-validation. learning-assistance уже охватывает преподавательское объяснение, реальные затруднения, альтернативы, аналогии и инструменты; переписывать её без причины не нужно.

Для режима добавляются проверяемые случаи завершения, полного задания из одной функции и запрошенного квиза. В основных SKILL.md эти правила уже написаны; их изменение требуется только при конкретном несоответствии. Альтернатива — заново сформулировать все четыре скилла — увеличивает риск отклониться от согласованных правил.

### 2. Устанавливать только выбранные имена

Предлагаемая команда для будущей документации:

```sh
npx skills add OWNER/REPO --agent codex --skill study-hint-normal study-hint-fast study-guide-normal study-guide-fast
```

Синтаксис выбора имён описан в [Skills CLI](https://github.com/vercel-labs/skills/blob/main/docs/commands.md). Установка из локального источника проверяется в отдельной временной папке с абсолютным путём к этому проекту вместо OWNER/REPO. Сам источник, пользовательские каталоги агента и глобальные настройки при испытании не изменяются; флаг глобальной установки не используется. Фактически использованную версию CLI записать в результат.

Проверять установленный локальный набор и содержимое policy-файлов, а не только exit code установщика. Для других клиентов сохраняется возможность выбора и текущая оговорка о непроверенном поведении. Короткая интерактивная команда остаётся допустимой как дополнительный вариант с явным предупреждением выбирать только study-режимы.

Альтернативы: свой установщик избыточен; изменение сгенерированных OpenSpec-файлов хрупко; --all и wildcard выбирают лишние скиллы; удаление локальных помощников мешает разработке.

### 3. Хранить небольшие кейсы и исходные данные проверки

Дополнить evaluation/ фикстурами, точными запросами, краткой инструкцией повтора и папкой результатов новых прогонов. Достаточно файлов Python с unittest для задач, где нужны запуск и diff, и Markdown для диалоговых кейсов. Новая runtime-зависимость учебным скиллам не нужна; общий runner, SDK или система оценок не требуются.

Каждый кейс описывает исходные файлы, запросы по ходам, выбранный режим и наблюдаемые критерии. Проверяющая сторона читает критерии; оцениваемому агенту передаются только скилл, запрос и нужная фикстура. Исходники фикстур копируются во временный каталог, проверки не меняют эталонные файлы.

Для нового прогона сохранить дату, версию Codex/доступные сведения о модели, SHA-256 реально поданного SKILL.md и policy-файла, запросы, фактический ответ, релевантные команды и вывод, изменения файлов и вывод проверяющего. Отсутствующие сведения отмечать как отсутствующие. Достаточны Markdown и текстовые файлы, схема БД не нужна. Фикстуры синтетические, секреты и посторонний локальный контекст в отчёты не включаются.

Существующий RESULTS.md сохранить как историческое ограниченное свидетельство. Не восстанавливать якобы точные старые ответы по памяти и не менять дату исторических результатов. Альтернатива в виде одних итоговых галочек не позволяет проверить основание вывода.

### 4. Проверять поведение, а не совпадение фраз

Ядро набора: hint не меняет целевую реализацию; псевдокод относится к текущему препятствию; guide не исполняет весь широкий запрос; конкретная часть выполняется с объяснением; полный запрос из одной функции не обходит план; понимание проверяется по просьбе, а не автоматически. Многоходовые кейсы покрывают разрешённые последовательные запросы guide и переключение/завершение режимов.

Пару normal/fast каждой категории сравнивать на одинаковом запросе и одинаковой фикстуре в отдельных свежих контекстах. Оценка — прямота, уместная подробность, причина рекомендации, границы помощи. Число слов можно сохранить как наблюдение, но оно не заменяет оценку. Непрошедший кейс нельзя объявить успешным после отбора удачного ответа.

Альтернатива — фиксированные длины и поиск обязательных фраз — проверяет стиль шаблона, а не пользу и соблюдение правил.

### 5. Разделить установку, нативное включение и прямую загрузку

После временной установки отдельно проверить в реальном Codex отсутствие автоматического включения без выбора, явный вызов каждого режима, переключение и завершение. Если этот путь нельзя запустить из доступного интерфейса, сохранить ручной чек-лист и статус not run, а не подменять проверку прямым чтением SKILL.md. Такой статус блокирует только заявление о проверенном нативном включении, а не доступность самих фикстур.

## Risks / Trade-offs

- Недетерминированные ответы → сохранять фактические результаты и границы smoke-проверок; повторение процедуры не означает идентичность ответов.
- Изменение CLI discovery → записать версию и проверить фактический состав установки; не обещать проверенную удалённую установку до публикации.
- Утечка полного решения через «пример» → оценивать смысл примера вручную, не только наличие кода.
- Слишком большой набор проверок → небольшие синтетические кейсы, повторное использование фикстур, без обязательных платных сервисов.
- Исправление правила ради одного удачного теста → сохранять рубрику и изменять инструкции только по воспроизводимому несоответствию.

## Migration Plan

При apply добавить кейсы и обновить документацию установки. После новых прогонов отдельно записать результаты, сохранив старые оговорки. Изменение основных спецификаций проходит обычный sync/archive после реализации, в ходе планирования они не редактируются.

Откат заключается в удалении добавленных материалов и возврате изменений документации/обоснованных правок скиллов. Глобальная конфигурация агентов и учебные проекты пользователей не затрагиваются. Адрес репозитория, бренд и лицензия остаются за пределами этого change и не блокируют локальную проверку.

## Уточнение задачи 4.1 от 18 ноября 2026

Два нативных прогона normal загрузили запрет, но выполнили прямую просьбу исправить файл. Проверяем гипотезу неоднозначного взаимодействия просьбы об исправлении и выбранного учебного режима; влияние других coding-скиллов пока не установлено.

План: явно определить диагностическое объяснение и следующий шаг ученика как результат hint-задачи, включая прямые просьбы об автоматическом исправлении; остальные coding-скиллы помогают исследованию и проверкам, но не меняют авторство. Смена авторства требует явного выбора guide или завершения учебного режима.

Проверка: свежие нативные контексты с одинаковыми фикстурами и запросом — старая normal как контроль, два запуска исправленной normal и один fast. Код проверяется побайтово, ответы оцениваются по прежней рубрике, события чтения скилла сохраняются. Старые неудачи сохраняются. Даже успешные прогоны не доказывают технического запрета или причинность гипотезы. Файловые ограничения клиента не добавляются.

### Результат эксперимента

Старая версия в новом контроле сохранила код; уточнённая normal изменила код в одном из двух прогонов. Формулировка не доказала исправление и исключена из продуктовых SKILL.md. Снимки и результаты сохранены в evaluation/runs/2026-11-18-hint-regression/. Следующий рассматриваемый вариант — ограничение записи со стороны клиента; навязать его через переносимый Markdown-скилл нельзя. Такое изменение команд запуска требует отдельного согласования продукта.
